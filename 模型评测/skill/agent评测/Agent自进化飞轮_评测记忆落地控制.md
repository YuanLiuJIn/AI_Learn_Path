# 评测→记忆→落地→控制：Agent 自进化飞轮怎么搭

> 来源文章：《评测→记忆→落地→控制：一篇讲透Agent自进化飞轮怎么搭》（作者 ethanytzhou，共同作者 yannisyang）
> 核心立场：① 进化的瓶颈是环节衔接；② 评测可信度 > 系统复杂度；③ 记忆核心是治理能力而非存储能力。
> 研读基础：Anthropic 递归自改进报告、斯坦福 CS329A、EvoAgentX 等；结合多个团队已验证实践。

---

## 〇、先对齐：自进化改的到底是什么（三层模型）

「自进化」被用得很滥。按「改什么」分三层：

| 层 | 改什么 | 持久性 | 成本/风险 | 说明 |
|---|---|---|---|---|
| Artifacts | 输出产物（自我纠错、多版迭代） | 无（任务结束 Agent 不变） | 低 | 打草稿，不是进化 |
| **Harness** | 配套系统（记忆/Skill/Prompt/工具配置/工作流） | 持久化到文件/库，跨会话生效 | 即时可控，可一键回滚 | **当前最具性价比的主战场** |
| Model | 模型参数（Agent RL、自对弈微调） | 最强 | 最高、风险最大 | 仍处研究阶段 |

**为什么 Harness 层是主战场**：改完立刻生效、改错一键回滚。实测数据（多个团队）：Harness 层进化使迭代次数减少 70%、Token 消耗降低 84%、某数据库 Agent Memory Token 节省 61%——一个模型参数都没动。

> 例：Agent 老在「日期格式转换」出错。Artifacts 层=本次多试几次；Harness 层=写一条 Skill 固化，下次直接 follow；Model 层=大量样本微调。绝大多数团队写条 Skill 即可。

## 一、信号——评测体系（飞轮第一齿）

### 1.1 评测的三重角色（被严重低估）
在自进化系统中评测不只是「上线前打分」，而是：
- **方向指引**：告诉系统哪里有问题，决定进化方向；
- **质量门控**：更新前验证「改了是否更好」，防退化；
- **经验筛选**：判断一次执行结果是好经验值得沉淀，还是坏经验应丢弃。

传统评测打错分=上线不够好的版本；自进化评测打错分=Agent 学到错误经验并污染后续所有任务（错误正反馈比没反馈更可怕）。所以**评测可信度 > 系统复杂度**。

### 1.2 七大核心难题（精度×成本×覆盖面三难）
1. **弱评估器（最致命）**：LLM 评 LLM 有系统性偏差（偏好长文本/特定格式/表面正确）。偏差会让 Agent 多轮「学会」骗过评估器——加速开往悬崖。
2. **评什么维度**：Agent 输出是「推理+工具调用+中间结果+最终答案」组合，只看结果漏掉幻觉碰巧答对、工具冗余、推理链错但记住答案等盲区。
3. **评什么粒度**：粗粒度（成败）便宜但不知错在哪；细粒度（每 step/tool call）精确但成本指数增长。建议日常粗筛、失败 case 细归因。
4. **开放式任务难量化**：写作/规划无确定对错。建议用偏好排序替绝对打分，或 AI 初筛+人复核流水线。
5. **评测集漂移**：业务在变但评测集半年不更新，数字漂亮用户骂街。
6. **预算公平性**：Best-of-N、多次重试取优带来的「提升」关掉预算就打回原形——必须在预算对等下比较。
7. **评测成本**：每次更新跑全量吃不消——用分层评测（轻量回归+定期全量）。

### 1.3 建设要点
- **手段分层**：底层规则/自动化校验（零成本、100% 客观，应充分利用）→ 中间 LLM-as-Judge（生成与评估模型分离、temperature=0、结构化输出、分维度独立评）→ 顶层人工抽样+元评测集（几十条绝对对错样本定期探评估器）。
- **评测集三分法**（互不泄漏，定期更新）：
  - train 50-60%：只用于诊断（暴露给生成修复的 LLM，不用于判好坏）；
  - val 20-30%：只用于筛选（绝不暴露给生成方，防记住答案）；
  - test 15-20%：最终验证（捕捉 val 过拟合但对新问题无效）。
  - 按问题类型分层抽样；val 每 2-4 周更新 20-30%，test 每 1-2 月更新。
- **终点是归因而非打分**：按失败类型走不同链路——系统性→触发 Skill/Prompt 更新+写 Playbook；偶发→写入记忆当反例；能力缺失→触发工具/能力补充（可用 Auto-Research）；回归→立即回滚标记 blocked。
  - 血泪教训：某场景连续 3 轮失败率 80%+ 不降，先查工具实现层（API 参数/服务端异常/数据没回来），而非在配置层打转。
- **评估器也要被评测**：四种互补机制（元评测集、人工抽检一致性、对抗样本、错误分析复盘）。

### 1.4 Skill 评测特殊性——四层验证证「真的有用」
1. **对照实验**：有/无 Skill 同跑，无 Skill 也能对=贡献为零（很多 Skill 只是和模型能力重叠）。
2. **难度校准**：case 太简单看不出差异，需有难度梯度（无 Skill 时部分对部分错）。
3. **轨迹追踪**：运行时真调用了 Skill 吗？还是占了位置没 follow。
4. **路径验证**：结果对但路径对吗？跳过了关键校验步骤=下次翻车。

## 二、积累——记忆系统（飞轮第二齿）

### 2.1 核心论断：记忆做不好比没有更差
多个团队加长期记忆后因检索噪声过高降级回无状态；有效记忆的 Agent 体验显著更好。**记忆真正难的是治理（什么该存/忘/怎么精准召回/不撑爆上下文），不是存储。** 像 Git 的价值在版本控制/分支/冲突解决而非「能存代码」。

### 2.2 三环矛盾与十大难点
- **写入环**：①价值判断难（什么值得永久存）②正负反馈不对称（成功不知因何成功）③粒度选择④隐性知识（「什么不能做」）难捕获。
- **存储环**：⑤记忆污染（错误记忆快速蔓延）⑥时效性衰减⑦冲突⑧存储成本失控。
- **读取环**：⑨检索噪声（向量近≠语义相关）⑩上下文预算分配。

### 2.3 建设要点一：写入——「策展而非全存」
- 正信号（用户确认/评测通过/任务成功）才写长期记忆；失败提取为「反例/陷阱」。
- **三层晋升**（临时记录→工作记忆→长期记忆），低门槛先解决「忘记记录」，再层层筛选提质。
- **非对称淘汰**：坏经验淘汰速度(−0.12)远快于好经验强化(+0.05)，约 2.4 倍。

### 2.4 建设要点二：存储——「分层架构 + 生命周期管理」
- 分层（业界共识）：L0 原始对话→L1 原子事实→L2 场景块→L3 用户画像。默认用顶层（轻量高密度），按需钻取下层。
- 生命周期：版本控制（版本号+来源标记）、演化能力（更新/合并/分裂/衰减）、主动遗忘（TTL/低频/负反馈淘汰）、冲突解决（后入优先+人工仲裁+乐观锁）。

### 2.5 建设要点三：读取——「渐进披露 + 严格预算」
- Step1 默认只注入顶层（Persona+Skill 前言，~500-800 token）；Step2 按需检索中层（语义+全文+精确三路并行 Top-K）；Step3 需时才钻取底层（node_id 回溯原始对话）。
- 严格预算：分层 Token 预算（Skill≤2000/Facts≤800/Profile≤500），单条≤200，最多注入 6 条。
- 反直觉发现：记忆建模为文件系统让 Agent 用 Bash/grep 管理，比造专用 API 更有效；符号化压缩（Mermaid 编码状态、日志卸载外部）可省 Token 61%、通过率 33%→50%。

## 三、落地——工程化（飞轮第三齿）

### 3.1 核心论断：自动化 ≠ 全自动
LLM 生成修复质量不可控（看不到历史决策/业务约束/API 规范，可能覆盖上次人工精心调整的逻辑）；单点修复缺全局视角（改 Skill A 破坏 Skill B 触发）；「总结→生成 Skill」需专门优化（训练过的小模型策展人优于冻结大模型）。**自动化覆盖「生成候选→评测→门控」，关键决策必须有人把关。**

### 3.2 完整链路八环节
1. **诊断归因**：失败分组、识别模式、定位环节（Prompt/Skill/工具/数据）。
2. **信号汇聚**：三路输入——本轮诊断 + 历史 Playbook + 外部知识（Auto-Research，破平台期）。
3. **生成候选**：Diff 模式（只输出修改片段，非全文重写）+ 注入背景知识。
4. **独立评测**：每个候选隔离环境验证（N 个候选×全量评测，故需控 N）。
5. **安全门控**：语法检查→回归检测→统计显著性→Playbook 一致性→人工确认。前四层自动过滤 95% 低质变体，人只审最后一步。
6. **灰度发布**：10% 流量 × 7 天观测（成功率/Token/延迟/反馈），P0 退化一键回滚。
7. **监控回流**：灰度新失败样本自动进下一轮种子池——上线是起点不是终点。
8. **经验沉淀**：有效方向/踩坑写入 Playbook（服务于「怎么改 Agent」，与通用记忆互补独立）。

> 本质：自进化工程化 = 「Agent CI/CD」。

### 3.3 关键建设要点
- **三路信号汇聚**防平台期（Cube-Harness AutoEvol 自行发现两条不在初始配置里的有效方向）。
- **安全门控分层**：自动在前人工在后。
- **灰度+回流**：10%×7 天，自动回滚是灵魂（半夜出事有人兜底）。
- **版本化一切**：版本号+变更日志+来源标记+关联评测结果，出问题可精准回滚。
- **Diff 模式**：只改片段，reviewer 秒懂、不碰无关逻辑、可精准回滚；多文件联动需 AST 签名验证（防隐蔽回归）。

### 3.4 Dreaming：异步「做梦」式进化
同步评测抓单次任务，看不到跨会话系统性模式（如 100 次会话中 30 次在时间格式转换出小错，单次看偶发、合看是短板）。Anthropic Dreaming（2026.5）：专职异步进程空闲时审阅历史轨迹，发现反复失败/低效/知识缺口，输出修订建议（最终由人决定，不直接改）。与同步评测互补（作业批改 vs 期中总结）。

## 四、控制——人机协作（飞轮第四齿）

### 4.1 核心论断：人的角色是教练和裁判，不是操作者
完全放手危险（Anthropic 警告：自主迭代自身配置会致隐蔽累积偏移，放大速度与飞轮转速成正比）；完全人工太慢。按场景**分级自主、渐进放权、动态升降级**。

### 4.2 五个必须有人的关键节点（刚性约束）
1. 规则级记忆写入前（全局遵循，错误规则危害巨大）；
2. Prompt/Skill 更新最终确认（尤其安全边界/拒答/权限——Agent 不应有能力改自己的安全约束）；
3. 评测发现回归时的决策（影响面判断）；
4. 新领域冷启动的初始经验种子（第一圈必须人推）；
5. 安全边界的设定与调整（Agent 不能自己决定自己权限边界）。

### 4.3 审核疲劳解法
- 层级一：自动化前四层门控过滤 95% 低质。
- 层级二：批量异步审核（攒一批附评测数据/影响面/输入输出对比/AI 推荐理由，让人做选择题）。
- 层级三：渐进放权+自动降级（连续稳定可升 Level，出回归自动降回）。

### 4.4 对齐漂移（更深层）
技术门控查「这次有无回归」（局部），不查「整体方向偏没偏」（全局）。例：评测无意奖励「详细」→ Agent 越来越啰嗦，每步门控通过但步步偏移。三层防护：①定期方向性审计（每月看 Skill 库/记忆/输出风格走向）②方向性约束指标（平均输出长度/工具调用次数/拒答率超阈值告警）③评测集显式含「意图对齐」维度（简洁性/格式/语气）。

## 五、飞轮——四齿咬合

### 5.1 四条数据通路（断任一则卡住）
1. 评测 → 记忆（好经验触发策展式写入）
2. 评测 → 落地（问题/差距信号驱动修复）
3. 落地 → 控制 → 生效（门控+人工后灰度上线）
4. 生效 → 下一轮评测（回流：成功正例入金标集，新失败回流为种子）

> 大多数团队问题：组件内部还行，但组件间「箭头」没自动化。

### 5.2 启动与持续
- **启动能量（人工推力，不能省）**：高质量初始评测集（花 1-2 周）、人工注入首批 Skill/记忆、清晰安全边界。
- **持续动力（自动回流）**：新失败样本自动回流、成功经验按晋升规则升 Skill、异步 Dreaming、Auto-Research 引入外部知识防枯竭。

### 5.3 易跑通的场景特征
- 评测信号来自**真实业务指标**（如真实 CTR/工单修复率），天然抗评测集漂移；
- **闭环链路短、反馈延迟低**（5 轮内见显著提升，否则团队易放弃）。

### 5.4 落地路线（先跑通 Phase 1）
- **Phase 1 最小闭环（1-2 周，人工 80%）**：50-100 条 case + Markdown 记忆 + 手动跑通完整闭环。验证闭环本身是否成立。
- **Phase 2 半自动（2-4 周，人工 40%）**：Skill 自动生成 + CI 评测门禁 + 版本管理 + 评测集三分法。
- **Phase 3 飞轮运转（1-2 月，人工 15%）**：灰度 + 回流 + 异步 Dreaming + 渐进放权。
- **Phase 4 元进化（持续，人工 5%）**：Auto-Research + 进化策略自优化 + 多 Agent 协同。
- 核心建议：**先跑通 Phase 1**——能手动转一圈的粗糙飞轮，好过精美但静止的蓝图。

## 六、三条原则（收束）

1. **评测可信度 > 系统复杂度**：先擦亮「眼睛」，再让「手脚」动。
2. **记忆是治理问题不是存储问题**：向量库≠记忆系统，治理能力（版本/遗忘/冲突/溯源/晋升）决定帮忙还是添乱。
3. **闭环价值在环节衔接而非单环节先进性**：环节间的「箭头」才是飞轮转不转的决定因素。

> 自进化不是功能，是系统设计范式——让每次执行不白费、每教训不白吃、每改进经验证。最难的是让四齿咬合持续转。
