# 02. 图数据模型：RDF、属性图、本体与 Schema

> 目标：理解知识图谱的底层表示方式：三元组、RDF、属性图、本体、Schema。

## 1. 知识图谱最小单元：三元组

知识图谱最基础的表达是三元组：

```text
(subject, predicate, object)
主语       谓词       宾语
```

例如：

```text
(爱因斯坦, 出生地, 乌尔姆)
(乌尔姆, 所属国家, 德国)
(相对论, 提出者, 爱因斯坦)
```

多个三元组连起来就是图：

```text
(相对论)-[提出者]->(爱因斯坦)-[出生地]->(乌尔姆)-[所属国家]->(德国)
```

## 2. 实体、关系、属性、概念

### 2.1 实体 Entity

现实世界中可以被唯一指代的对象。

```text
人物：爱因斯坦、姚明
地点：北京、巴黎
组织：某大学、某医院
作品：相对论、某篇论文
药品：阿司匹林
疾病：糖尿病
```

### 2.2 关系 Relation

实体和实体之间的连接。

```text
出生地
任职于
治疗
引用
属于
投资
控制
```

### 2.3 属性 Attribute

实体自身的描述。

```text
姓名：爱因斯坦
出生日期：1879-03-14
身高：226cm
药品剂量：100mg
```

### 2.4 概念 Concept / Class

实体所属的类别。

```text
爱因斯坦 是 科学家
阿司匹林 是 药物
糖尿病 是 疾病
Transformer 是 模型架构
```

## 3. RDF 数据模型

RDF 是语义网中的标准知识表示方式。

RDF 的核心就是三元组：

```text
<subject> <predicate> <object> .
```

例如：

```text
<Einstein> <bornIn> <Ulm> .
<Ulm> <locatedIn> <Germany> .
<Einstein> <type> <Scientist> .
```

RDF 强调：

```text
全局 URI 标识
标准语义
可跨系统共享
适合本体推理
```

## 4. RDF 的优点和缺点

优点：

```text
标准化程度高
适合语义互操作
支持 SPARQL
支持 RDFS/OWL 本体推理
适合开放知识库
```

缺点：

```text
建模相对抽象
对工程人员不如属性图直观
复杂属性表达比较啰嗦
图算法和业务开发体验依赖具体系统
```

## 5. 属性图 Property Graph

属性图更贴近工程开发。

它包含：

```text
节点 Node
边 Edge
标签 Label
属性 Property
```

例如：

```text
(:Person {name: 'Einstein', birthDate: '1879-03-14'})
(:City {name: 'Ulm'})
(:Person)-[:BORN_IN]->(:City)
```

边也可以有属性：

```text
(:Person {name:'张三'})-[:WORKS_AT {start:'2020', role:'Engineer'}]->(:Company {name:'A公司'})
```

## 6. 属性图的优点和缺点

优点：

```text
直观易懂
适合工程开发
边和节点都能带属性
路径查询体验好
适合推荐、风控、关系分析
```

缺点：

```text
语义标准化弱于 RDF
跨系统互操作成本较高
本体推理不是原生强项
```

## 7. RDF vs 属性图

| 维度 | RDF | 属性图 |
|---|---|---|
| 基本单元 | 三元组 | 节点、边、属性 |
| 查询语言 | SPARQL | Cypher / Gremlin / GQL |
| 标准化 | 强 | 相对弱，但工程友好 |
| 本体推理 | 强 | 通常需要额外实现 |
| 开发体验 | 语义严谨 | 更直观 |
| 适合场景 | 开放知识库、语义互操作、本体推理 | 业务图谱、推荐、风控、路径分析 |

简单选择：

```text
需要标准语义和本体推理 → RDF / OWL
需要工程开发和路径分析 → 属性图
```

## 8. 什么是 Schema？

Schema 是图谱的结构约束。

例如医疗图谱：

```text
实体类型：
  Disease, Symptom, Drug, Department, Checkup

关系类型：
  Disease -[has_symptom]-> Symptom
  Disease -[treated_by]-> Drug
  Disease -[belongs_to]-> Department
  Disease -[needs_checkup]-> Checkup
```

Schema 的作用：

```text
规定有哪些实体类型
规定有哪些关系类型
规定哪些关系允许连接哪些类型
规定属性字段和取值范围
提高数据一致性
方便查询和推理
```

## 9. 什么是本体 Ontology？

本体比 Schema 更强调“概念体系”和“语义规则”。

例如：

```text
外科医生 是 医生 的子类
医生 是 职业 的子类
心脏病 是 疾病 的子类
治疗关系 的 domain 是 药物
治疗关系 的 range 是 疾病
```

本体可以表达：

```text
类层级：A 是 B 的子类
关系约束：某关系只能连接哪些类型
等价关系：A 等价于 B
互斥关系：A 和 B 不能同时成立
传递关系：如果 A 位于 B，B 位于 C，则 A 位于 C
```

## 10. Schema 和本体的区别

| 维度 | Schema | Ontology |
|---|---|---|
| 重点 | 数据结构 | 语义规则 |
| 作用 | 约束数据格式 | 支持推理和语义解释 |
| 复杂度 | 相对简单 | 更复杂 |
| 常见场景 | 业务图谱建模 | 语义网、医疗、科研、知识推理 |

可以这样理解：

```text
Schema 告诉你“数据长什么样”
Ontology 告诉你“这些概念之间的语义关系是什么”
```

## 11. 建模时最容易犯的错误

### 11.1 把属性建成实体，或把实体建成属性

例如：

```text
年龄通常是属性：Person.age = 18
城市通常是实体：(Person)-[出生地]->(City)
```

判断标准：

```text
如果它还会参与更多关系，建成实体
如果只是描述某个对象，建成属性
```

### 11.2 关系粒度不一致

错误：

```text
治疗
可能治疗
常用治疗
一线治疗
```

关系太乱会导致查询困难。应先定义清楚关系层级和命名规范。

### 11.3 没有实体 ID 体系

同一个实体可能有多个名字：

```text
北京大学
北大
Peking University
```

必须有统一 ID，否则图谱会碎裂。

## 12. 一句话总结

> 知识图谱的底层建模围绕实体、关系、属性和概念展开。RDF 适合标准语义和本体推理，属性图适合工程开发和路径分析。Schema 规定图谱结构，本体表达概念语义和推理规则。建模质量决定了图谱后续查询、推理和应用的上限。
