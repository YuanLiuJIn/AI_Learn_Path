# 05. 奖励设计

> 目标：理解 Agent RL 中奖励信号的设计哲学，以及 Outcome Reward、Process Reward、Rule-based Reward 的区别。

## 1. 奖励 = 训练的指挥棒

```text
RL 的本质是：用奖励信号引导模型往好的方向走。

奖励错了 → 模型学到错的行为
奖励太稀疏 → 模型学不到东西
奖励太好骗 → 模型学会 Reward Hacking
```

## 2. 三类奖励信号

### 2.1 Outcome Reward（结果奖励）

```text
只看最终结果，不管过程

例子：
  代码是否通过测试 ✅/❌
  数学题答案是否正确 ✅/❌
  任务是否完成 ✅/❌

优点：简单、客观、不会 Reward Hacking
缺点：稀疏、中间步骤没有信号
```

### 2.2 Process Reward（过程奖励）

```text
每一步都给奖励，引导模型走正确的过程

例子：
  工具调用成功 → +0.1
  编译通过 → +0.3
  测试通过 → +0.5
  最终完成 → +1.0

优点：密集信号、训练更容易
缺点：需要设计规则或训练 PRM
```

### 2.3 Rule-based Reward（规则奖励）

```text
用规则自动判断，不需要 Reward Model

例子：
  格式是否正确（JSON 格式、代码规范）
  长度是否合理（不要太短也不要太长）
  是否使用了正确的工具

优点：零成本、可大规模扩展
缺点：只能覆盖有明确规则的任务
```

## 3. Process Reward Model

### 为什么需要 PRM？

```text
多轮任务往往只有最终结果才有明确奖励
中间步骤缺乏信号 → 训练困难

PRM 给每一步打分，让训练信号更密集
```

### AgentPRM 框架

```text
核心思想：
  1. 用 Monte Carlo 采样评估每个 step 的价值
  2. 训练一个 PRM 预测每个 step 的价值
  3. 用 PRM 给每一步提供奖励信号

Monte Carlo 评估：
  从某个 step 开始，随机采样多条后续路径
  统计最终成功/失败的概率
  成功率高 → 这个 step 是好 step
  成功率低 → 这个 step 是差 step
```

### InversePRM

```text
核心思想：
  直接从成功轨迹中学习 PRM
  不需要 Monte Carlo 采样

假设：
  成功的轨迹中，每一步都是"好的"
  失败的轨迹中，某些步骤是"坏的"

训练：
  给成功轨迹的每一步打高分
  给失败轨迹的每一步打低分
```

## 4. 奖励设计的关键原则

### 原则 1：奖励要可验证

```text
好奖励：代码通过测试、答案正确、任务完成
  这些是客观事实，无法造假

差奖励：回答"看起来不错"、"风格优美"
  这些是主观判断，容易 Reward Hacking
```

### 原则 2：奖励密度要合适

```text
太稀疏 → 训练困难，模型不知道哪一步做对了
太密集 → 模型过度关注小奖励，忽略大目标

推荐：最终奖励（权重高）+ 中间奖励（权重低）
```

### 原则 3：防止 Reward Hacking

```text
Reward Hacking：模型找到奖励函数的漏洞
  例如：重复输出"正确"的词来获取高分

防御手段：
  多维度奖励（不是单一分数）
  KL 惩罚（防止偏离原始模型太远）
  人类抽检
  规则约束
```

### 原则 4：奖励要可扩展

```text
好的奖励设计应该能自动产生海量训练数据

数学题 → 自动判断对错
代码 → 自动跑测试
游戏 → 自动判断通关

不需要人类标注 → 可以无限扩展
```

## 5. 和你项目的关联

### UE5 测试 Agent 的奖励设计

```text
Outcome Reward：
  测试全部通过 → +10
  测试部分通过 → +3
  测试全部失败 → -5
  游戏崩溃 → -10

Process Reward：
  每步操作成功 → +0.1
  性能指标正常 → +0.2
  状态断言通过 → +0.3
  发现 Bug → +2

Rule-based Reward：
  步骤数合理 → +0.5
  使用了正确的 Action → +0.2
  JSON 格式正确 → +0.1
```

## 6. 一句话总结

> 奖励设计是 Agent RL 的灵魂。Outcome Reward 简单可靠但稀疏，Process Reward 密集但需要额外训练，Rule-based Reward 零成本但覆盖面有限。好的奖励设计要可验证、密度合适、防 Reward Hacking、可扩展。
