# 02. 上下文工程

> 目标：理解上下文管理的核心挑战、五层分区机制、自动压缩、Memory 系统和稳定前缀设计。

## 1. 上下文设计的不可能三角

上下文设计面临三个互相冲突的目标：

```text
          精准性
          /  \
         /    \
        /  ⚠️  \
       / 不可能  \
      /  同时最优  \
     /            \
    /              \
   /________________\
经济性              效率性

三者只能取其二：
  追求精准+效率 → 成本高（大上下文）
  追求精准+经济 → 效率低（频繁裁剪重建）
  追求效率+经济 → 精准度下降（激进裁剪）
```

### 三个目标的含义

```text
精准性（Accuracy）
  提供准确、完整的信息
  让 LLM 正确理解用户意图
  避免关键信息丢失

效率性（Efficiency）
  提高模型缓存命中率
  减少响应延迟
  优化上下文结构

经济性（Cost-effectiveness）
  控制 Token 使用量
  降低 API 调用成本
  减少冗余信息
```

## 2. 核心挑战

上下文管理面临多维度挑战：

| 挑战维度 | 具体问题 | 影响 |
|---|---|---|
| 信息完整性 | 裁剪过度、关键信息丢失、上下文断裂 | 准确度下降、重试率上升 |
| 信息效率 | 无关信息过多、LLM 注意力分散 | 成本增加、响应变慢 |
| Cache 命中率 | 前缀频繁变化、消息顺序不稳定 | 成本大幅上升、延迟增加 |
| 长期记忆 | 历史消息积累、跨会话知识丢失 | 窗口溢出、重复探索 |
| 上下文组织 | 信息混乱无序、结构不稳定 | 理解困难、Cache 失效 |

## 3. 五层分区机制

核心思想：按功能和稳定性将上下文分为五个区域，不同区域采用不同的管理策略。

### Zone 1：系统区（完全固定 ★★★★★）

```text
内容：
  系统角色描述
  通用工作流程说明
  编程规范和最佳实践
  安全约束和注意事项

特性：
  完全固定，所有请求共享
  100% 可缓存，显著降低成本
  版本化管理，迭代可控

大小：约 5-8K tokens
```

### Zone 2：工具区（半固定 ★★★★☆）

```text
内容：
  工具分类摘要（渐进式发现第一层）
  按需加载的工具详细描述
  工具使用示例和注意事项

特性：
  工具集固定时可缓存
  渐进式加载，按需提供详情
  分层描述（摘要 → 列表 → 详情）

大小：初始 ~0.5K，按需扩展到 5-10K
```

### Zone 3：环境区（准静态 ★★★☆☆）

```text
内容：
  操作系统和工作空间路径
  项目文件结构
  Git 状态信息
  用户规则和编码偏好

特性：
  会话内相对稳定
  结构化组织，便于引用
  按需更新（文件变化时）

大小：约 2-5K tokens
```

### Zone 4：记忆区（长期持久 ★★★★☆）

```text
内容：
  用户偏好和工作习惯
  项目特定知识（架构、关键文件）
  历史决策和设计模式
  常见问题解决方案

特性：
  跨会话持久化存储
  相关性检索注入
  自动更新和淘汰

大小：按相关性注入 ~1-3K tokens
```

### Zone 5：对话区（高度动态 ★☆☆☆☆）

```text
内容：
  历史对话消息（自动压缩）
  工具调用及其结果
  用户引用的文件内容
  当前任务的临时上下文

特性：
  动态变化，每步更新
  智能裁剪和压缩
  分级管理（完整/关键/摘要）

大小：动态，通常 10-40K tokens
```

## 4. 自动压缩机制

### 触发条件

```text
条件 1：上次请求的 Token 数量接近模型输入限制
条件 2：总步骤数超过阈值

任一条件满足 → 触发压缩
```

### 压缩流程

```text
Step 1：选择压缩目标
  保留最近 N 轮完整内容
  压缩中间轮次关键信息
  总结早期轮次为摘要

Step 2：生成压缩摘要
  调用 LLM 进行总结
  提取关键决策和模式
  保留重要的工具调用
  标注未解决的问题

Step 3：替换历史消息
  删除被压缩的详细消息
  插入结构化压缩摘要
  标记压缩点 ID

Step 4：更新 Memory
  提取长期有价值的知识
  存入 Memory Zone
```

### 压缩摘要结构

```text
[压缩历史 - ID: xxx]

时间范围：Rounds 1-3 (Steps 1-18)

关键操作：
  - 创建了 Web 项目并配置开发环境
  - 集成了数据库和 ORM 工具

重要决策：
  - 认证策略：基于 Token 的认证方案
  - UI 技术栈：选择轻量级方案

技术细节：
  - 关键配置：数据库连接、API 端点
  - 重要文件：认证模块、数据模型

待解决问题：
  - 邮件验证功能待实现
```

## 5. Memory 机制

通过文件系统持久化用户偏好和项目知识。

### 两层架构

```text
Layer 1：用户偏好层
  编程风格偏好、技术栈偏好、命名规范等
  来源：自动学习 + 用户显式设置

Layer 2：项目知识层
  架构信息、关键文件、常用命令、已知问题
  来源：从对话中自动提取
```

### Memory 生命周期

```text
创建 → 加载（对话初始化时） → 更新（对话过程中） → 管理（版本控制）
```

## 6. 稳定前缀设计

核心思想：将可缓存的固定内容放在前面，动态内容放在后面。

```text
固定部分（可缓存，Cache Key 的一部分）：
  System Zone（角色描述、流程、规范）
  Tool Zone（工具集固定时）
  Environment Zone 的稳定部分

动态部分（不缓存）：
  Memory Zone（相关性动态）
  Conversation Zone（高度动态）
```

### 保持前缀稳定的技巧

```text
1. 固定顺序：工具列表按字母序排列
2. 标准化格式：统一的消息结构
3. 避免动态时间戳：不在 System Prompt 中放当前时间
4. 版本化管理：System Prompt 版本化，变更时整体更新
```

## 7. 一句话总结

> 上下文管理的核心是"在有限窗口内最大化信息价值"。五层分区按稳定性分离内容以提升 Cache 命中，自动压缩在完整性丢失前主动精简，Memory 实现跨会话知识复用，稳定前缀让固定内容被充分缓存。
