# Agent Skill 评测方法：从文档体检到能力验证

> 来源文章：《Agent Skill 评测方法：从文档体检到能力验证》（作者 hugoho）
> 核心观点：Skill 质量不能压缩成一个总分，需从静态完成度、路由表现、工具执行价值、文本输出增益、token 成本五个维度分开看。

---

## 〇、为什么要单独评测 Skill

普通 Prompt 评测看最终回答；Skill 更像「能力包」，内含触发描述、执行步骤、工具依赖、脚本、领域知识、权限边界、输出格式。一个 Skill 至少要回答五个问题：

| 问题 | 对应评测 |
|---|---|
| 写得完整吗 | 静态结构检查 |
| 该触发时能触发吗 | 路由表现验证 |
| 注入后回答更好吗 | 输出对比实验 |
| 工具调用路径正确吗 | 端到端轨迹评测 |
| 消耗的上下文划算吗 | 成本与收益观察 |

这些评测彼此相关但**不能互相替代**。

## 一、两组评测样本

| 样本 | 数量 | 特征 |
|---|---|---|
| 内部仓库 | 244 | 工具依赖重、MCP/API 多、脚本与内部数据源多、相似任务族多（路由混淆风险高）、接近生产场景 |
| 社区样本 | 56 | 以 SKILL.md 为主、元数据不统一、description 多为英文、很多无脚本、任务跨度大、同质化低 |

## 二、评测设计（5 部分）

### 2.1 静态 8 维度体检（满分 100，适合准入体检）
| 维度 | 权重 | 看什么 |
|---|---|---|
| 执行流程 | 20 | 步骤、顺序、代码块、输出说明 |
| 路由能力 | 15 | description 长度、触发条件、排除边界 |
| 脚本自动化 | 15 | scripts/、工具脚本、引用关系 |
| 防呆容错 | 10 | 前置条件、警告、fallback、自检 |
| 知识密度 | 10 | references、正文结构、领域材料 |
| 安全与信任 | 10 | 密钥泄露、危险操作、权限声明 |
| 路由混淆 | 10 | 与其他 Skill 的 description 重叠度 |
| 工程规范 | 10 | 元数据、版本、目录整洁度 |

### 2.2 路由实测
为每个 Skill 生成正向 / 负向 prompt，让模型在技能池中选择最匹配者，用精确率、召回率、F1 衡量。

### 2.3 输出对比（A/B）
同一任务跑两种条件：baseline（不注入 Skill）vs with-skill（注入 SKILL.md），打乱后让 judge 模型判哪份更好。适合评估知识补充、结构化模板、专业表达、格式约束等**文本可观察增益**；对依赖真实 API/浏览器/命令行/账号数据的 Skill 易失真。

### 2.4 工具感知标注
凡依赖外部工具/API/浏览器/命令行/账号/文件操作/真实副作用的，标记为「工具/外部系统依赖型」，其 A/B 文本胜负只作观察项，不作质量结论。

### 2.5 上下文成本与收益（Token ROI，小样本）
记录 baseline 与 with-skill 的 token 消耗。计算口径：

- 单轮净 token 收益 = baseline 总 token − with-skill 总 token
- Skill 上下文成本 = with-skill prompt − baseline prompt
- Token ROI = 单轮净收益 / 上下文成本

## 三、核心结果与发现

### 3.1 总体结果
| 指标 | 内部 244 | 社区 56 |
|---|---|---|
| 静态平均分 | 58.4 | 60.5 |
| 路由 F1 均值 | 0.820（237 有效） | 0.793（40 有效） |
| 原始 A/B | Skill 胜 72 / 裸模胜 167 / error 4 | Skill 胜 23 / 裸模胜 28 / error 51 |
| 安全问题 | 117 未声明工具依赖、21 硬编码密钥等 | 8 硬编码 key、1 危险删除 |
| 混淆问题 | 25 个 Skill 混淆扣分，53 条 top-conflict | 整体混淆较低 |

### 3.2 静态短板不同
- **内部样本**：治理问题为主——工具依赖未声明、密钥硬编码、相似 Skill 混淆、降级与自检不足（防呆容错仅 4.0/10）。
- **社区样本**：生产化不足——脚本少、自动化弱（脚本自动化仅 2.9/15）、description 不写排除边界（路由能力仅 5.8/15）。

### 3.3 路由：技能池越同质化，排除边界越重要
内部 F1 略高但混淆更严重（25 个 Skill 扣分）。路由评测至少分两层：
1. 单个 Skill 的正向触发 + 负向排除；
2. 同任务族 sibling skill 之间的 confusion set（如「分析最近工单」可能命中三四个相似候选）。

### 3.4 输出 A/B：工具类 Skill 需要更合适的环境
56 个社区样本里 51 个依赖工具/外部系统；内部大量 tie 本质是评测环境没给 Skill 展示能力的空间。工具类典型价值链：

```
识别任务 → 鉴权/环境检查 → 调工具/API → 处理返回值 → 渲染/写入/执行 → 校验结果
```

纯文本 A/B 只看最后一段回答，前面的工具链缺席。**这类 Skill 更适合端到端沙箱**：提供真实/模拟工具、返回值、错误状态，检查调用顺序、参数正确率、失败恢复、最终断言。

| 场景 | 纯文本 A/B 是否适合 | 原因 |
|---|---|---|
| 知识增强型 | 适合 | 增量知识直接体现在回答 |
| 格式模板型 | 部分适合 | 能观察结构/格式改善 |
| 工具编排型 | 不适合 | 缺少真实工具和返回值 |
| 报表/诊断/数据拉取型 | 不适合 | 价值在取数、处理、校验 |
| 多轮工作流型 | 不充分 | 单轮看不到返工/恢复 |

### 3.5 Token ROI：单轮看是成本，完整任务才可能有收益
补测 5 个样本，单轮净收益**全为负**（多注入一段上下文，单轮难立刻省回）。真正价值在完整任务级别：少问澄清、少写临场计划、少走错工具路径、少一次格式返工、少一次错误恢复。单轮 ROI 只提示上下文成本；完整任务 ROI 需记录总轮次、总 token、工具重试次数、断言通过率。

### 3.6 安全和治理适合做准入门槛
两组都暴露硬编码密钥、危险删除等。不依赖评测环境，适合提交前拦截：密钥扫描、危险操作扫描、权限声明检查应成基础门槛。

### 3.7 多维错位比排名更重要（匿名样本）
样本 I01（内部 S 级，F1 0.86，tie）：工具链完整，纯文本 A/B 看不出价值。
样本 C02（社区 53 分，F1 1.00，Skill 胜）：流程约束带来输出改善。
样本 C03（社区 37 分，F1 0.86，Skill 胜）：静态低分仍可能有领域知识增量。
→ Skill 质量不是单维排名，要综合看静态完成度、入口路由、文本增益、工具价值、token 成本。

## 四、一套更稳的 Skill 评测流程（四层）

- **第 1 层：准入体检**——frontmatter 完整、description 存在、无硬编码密钥、无危险操作、工具/MCP 权限声明、目录可读、版本有效。解决「能不能进入市场」。
- **第 2 层：路由验证**——正向触发、负向排除、sibling confusion、holdout/adversarial holdout、family-level 回归。解决「用户说出需求时能不能找到它」。
- **第 3 层：类型判定**——知识增强型（A/B、事实覆盖、知识增量）/ 工具编排型（工具轨迹、参数正确率、失败恢复）/ 流程固化型（步骤顺序、返工次数、Token ROI）/ 路由入口型（F1、混淆矩阵、family 回归）/ 角色设定型（多轮稳定、边界控制、领域一致）。决定后续评测环境。
- **第 4 层：能力验证**——文本型（输出断言 + A/B）、工具型（端到端沙箱 + 工具轨迹）、流程型（完整任务 token/轮次/返工）、高风险型（权限边界、安全红队、失败恢复）。真正回答「有没有带来能力增益」。

## 五、最后判断

Skill 是**压缩后的执行经验**，会消耗上下文，必须换来某种增量：知识增量、流程稳定性、工具调用可靠性、或更少的返工。一个只把模型本来就懂的常识写进 SKILL.md 的 Skill，在强模型面前难有价值；能固化专有知识、执行路径、错误处理、工具顺序、输出断言的 Skill，才有机会提升 Agent 可靠性。

**下一代 Skill 评测围绕三个问题**：
1. 它提供了什么增量？
2. 这种增量应该在什么环境里验证？
3. 它消耗的上下文和维护成本，换来了多少稳定性和少返工？

回答完这三点，评测才算从文档体检走向能力验证。
