## 一、LLM-Based Agent 简介

基于 LLM 的智能体（LLM-based Agent，下文多简称 Agent）是当前 LLM 实现**落地应用**最主要的方式。以 Claude Code 为代表的编程智能体已取得亮眼成功，成为开发提效利器；Manus 这类日常办公智能体被 Meta 收购，也侧面印证了 Agent 在商业上的重要性。

### 1.1 什么是 Agent

最通俗的解释是「机器人」；从学术角度，Agent 是「能够与环境进行互动、并做出反应的智能存在」。

定义里有三个要素：**智能、环境、交互**。

- **大脑（智能）**：Agent 的核心，对 LLM-based Agent 而言就是 LLM。
- **环境**：Agent 所在的外部世界，是获取信息与施加影响的所在。
  - 聊天机器人：环境是与它对话的用户。
  - 编程 Agent：环境是代码仓库、文件系统等。
- **交互**：分「信息载体」与「交互手段」两部分（见 1.3）。

### 1.2 信息载体与交互手段

- **信息载体**：LLM 如何读取/输出信息。文生文模型只有文本；多模态模型可接受文本、图片、音频、视频等更丰富的媒介，输出同理。
- **交互手段**：LLM 如何获取信息并对环境施加影响，仅靠 LLM 自身无法完成，需要外部系统配合，**最主要的方式是以「Tool（工具）」的形式与环境交互**。

示例：

```text
获取天气：
  Agent 输出指令 get_weather(date="20251214", location="北京")
  → 外部系统解析 → 调用天气 API → 文本返回结果给 LLM

删除文件：
  Agent 输出指令 delete(file_path="/data/file1")
  → 外部系统解析 → 调用操作系统接口完成删除 → 返回成功与否
```

本质：**获取信息 + 对环境施加影响，造成环境状态改变**。

### 1.3 think–action–observation 迭代与 trajectory

Agent 与环境的交互是反复迭代的过程，可简化为：

```text
query → think → action → observation → think → action → observation → … → end
```

即「**think–action–observation**」循环，直到任务完成或终止。这样一串完整步骤叫一条**轨迹（trajectory）**，是 Agent 解决某任务的完整过程。

### 1.4 脚手架 Scaffold

一个可用的 LLM-based Agent = 「作为智能核心的 LLM」+「帮助它与外部环境交互的系统」。

这套系统的作用：

1. 向 LLM 传递输入与输出；
2. 预置工具，解析 LLM 输出、进行工具调用、把结果返回 LLM；
3. 负责整个任务执行流程（接收任务、调度 LLM 跑完 think–action–observation 循环）。

这套系统的专业称呼是**脚手架（Scaffold）**。例如：

- **Manus**：一套提供丰富工具、优化迭代交互的脚手架；
- **Claude Code**：专注编程开发场景、接入自家 LLM 的脚手架。

## 二、Agent 的评估

### 2.1 Agent 任务的特点

#### 什么是「Agent 任务」

从「完成任务的方式」定义：大体遵循 think–action–observation 迭代循环来完成的任务。它与「数学 / 写作」等**不是同一维度**的概念——我们完全可以用 Agent 形式解数学题（调用工具查资料、用计算器），二者正交。

与 Agent 任务并列的任务类型（同按「完成方式」划分）：

| 任务类型 | 含义 |
|---|---|
| 单轮任务 | 不涉及历史对话，只通过一轮对话完成，不需要迭代与工具调用 |
| 非 agent 的多轮任务 | 涉及历史对话消息，但只需一轮对话完成，输入中包含之前的对话历史 |
| agent 任务 | 大体遵循 think–action–observation 迭代循环，基本涉及工具调用与环境交互 |

#### Agent 任务与其它任务的区别

| 任务特性 | 说明 |
|---|---|
| 多轮迭代 | 多次 think–action–observation，伴随多次 LLM 调用 |
| 搭配脚手架 | 无法脱离具体脚手架单独评测「LLM」的 agent 表现，最终结果 =「LLM + 脚手架」共同结果 |
| 工具调用 | 执行中涉及外部工具调用，可能是 fake 假工具，也可能是真实工具（如网页搜索） |
| 需要外部环境 | 执行有赖于与某外部环境交互，不同任务环境差异很大 |

这些特性导致 Agent 表现：

1. **执行时间长**：多轮迭代、多次 LLM 与工具调用，每环节都增时；
2. **执行成本高**：多次 LLM 调用增加成本，真实工具调用另有成本；
3. **结果不稳定**：多轮 + LLM 输出随机性 + 外部工具/环境不稳定，比单轮任务更不稳定；
4. **过程不唯一**：同一任务有多种思路，每次执行路径往往差异很大。

### 2.2 评估 Agent 与评估其它任务的不同

上述特性使得 Agent 评测与单轮任务评测有差别：

1. **最终结果检查途径更全面**：很多情况下结果涉及环境状态检查，不止在 LLM 回复里；
2. **更关注表现稳定性**；
3. **对执行成本更敏感**。

同时，Agent 任务步骤更长，涉及多种能力项：

- **任务规划**：规划更高效的解决方案；
- **工具调用**：从工具列表选最合适的并正确调用；
- **反思**：针对未达预期的中间结果快速分析、调整方案；
- **记忆**：复杂 Agent 有额外记忆模块，能否有效利用以处理长程信息。

### 2.3 Agent 评估系统组成

一个 Agent 评测系统通常由以下部分组成：

| 概念 | 中文 | 解释 |
|---|---|---|
| task | 任务 | 评测集里要求 Agent 处理的具体任务，如「帮我买一张北京到上海的机票」 |
| trial | 尝试 | 每次完成某任务的过程叫一次尝试；因看重稳定性，常多次尝试 |
| outcome | 结果 | 完成后的结果，既体现在最终回复（「已帮你订了机票」），也体现在环境状态（「官网上确实能查到预定记录」） |
| grader | 评分器 | 对表现打分的组件；Agent 评估中常有多个评分器，从不同角度度量（完成度 / 成本 / 稳定性等） |
| evaluation suite | 评估集 | 评估任务的集合，针对某领域 / 能力项做针对性评估 |
| evaluation harness | 评估框架 | 运行整个评估流程的实现框架，可批量评估、轨迹收集、结果打分、统计，端到端 |

> 注：`trajectory`（轨迹）、`Agent harness`（脚手架）等概念见第一节。

### 2.4 评估维度（评什么）

| 维度 | 说明 |
|---|---|
| 执行结果 | 是否正确完成任务，通常检查 LLM 最终回复 + 环境状态 |
| 执行成本 | 消耗 token、换算金钱成本、交互轮数、执行时间 |
| 表现稳定性 | 多次尝试是否每次都成功，用 **pass^k**（要求 k 次全部成功）度量 |
| 潜力高低 | 多次尝试是否至少一次成功，用 **pass@k**（k 次中至少一次成功）度量 |
| 执行过程 | 复杂多步任务若只看成败，难区分能力差异（差一步 vs 一开始就错）；一般通过对轨迹分析（是否完成某关键工具调用等）评估 |
| 核心能力 | 对规划、工具调用、反思优化、记忆等能力专项评估 |

## 三、评分器介绍（如何评）

评分器是评估系统的核心组件。Agent 任务涉及的评分器类型与其它任务差别不大，主要区别在于：Agent 任务常涉及环境状态检查，导致评分器**数量更多、能力更全面（如检查某图表是否正确）、或需更资深专家参与**。

按实现方式分三类：

### 3.1 基于代码 / 规则的评分器

用代码方式评估。优点：快速、稳定、客观；缺点：缺乏灵活性（输出稍变可能失效）、无法语义层校验、无法判断「页面布局是否错乱」等。

Agent 中特有的一些评分器：

1. **工具调用检查**
   - 通过字符串匹配、语法解析，判断工具调用的准确性；
   - 根据执行结果是否匹配，检查 Agent 执行过程中的工具调用与标准结果中涉及工具调用的一致性。
2. **执行进度分析**
   - 匹配轨迹中的工具调用序列与标准轨迹的工具调用序列，判断最后进展程度。
3. **环境状态检查**
   - 如执行某个脚本，检查数据库中某条记录是否被删除。

### 3.2 基于模型 / Agent 的评分器

用其它 LLM 模型打分。优点：灵活、泛化好、可判断的检查项范围更广；缺点：不稳定、可能出错、成本更高。

除 LLM 外，复杂任务有时用另一个 agent 来评判，例如：

- 涉及交互功能验证的场景（如 bolt.ai 用浏览器 agent 验证 app 开发结果）；
- 准确性要求高又想适配不同输出的场景（如调用外部库校验两个复杂公式一致性）；
- OpenAI 对 GDPEval 这类多样化输出任务，设计了一套基于 agent 的自动评分器。

### 3.3 基于人工的评分器

用人工评估。优点：上限高，理论上可准确评估任何结果；缺点：成本高、效率低、资源稀缺（某些任务需领域专家）、有额外培训成本。

## 四、常见 Agent 评估场景

下面介绍几类典型 Agent 评估场景。

### 4.1 Web 交互

评估 Agent 操作浏览器、完成各类任务的能力。大多数通过检查浏览器最后的 URL、网页状态等方式对执行结果打分。常见评估集：

- **MiniWoB**：一系列简单任务（点击按钮、填写虚拟邮件和日历表单），使用合成简单环境。
- **FormWoB**：表单填写任务，评估处理结构化输入的能力。
- **WebShop**：模拟在线购物场景，在多步决策与理解用户偏好方面挑战 Agent。
- **WebArena**：基于真实网站构建模拟环境，涵盖各种网络交互任务，测试泛化能力；变体 **VisualWebArena**、**VideoWebArena** 分别加入视觉信息与视频教程。
- **REAL**：利用确定性快照重建 11 个高保真网站模拟，将基于脚本的状态验证与基于 LLM 的评分标准结合，用于开放式检索任务。
- **TheAgentCompany**：模拟小型软件公司环境，聚焦真实世界专业场景表现。
- **Mind2Web**：要求理解丰富页面结构并规划多步目标；**Online-Mind2Web** 进一步引入动态内容变化与实时 DOM 变动挑战。
- **WebVoyager**：强调对中间状态有效建模，以及不同页面间长期依赖关系推理。
- **WebLINX**：专注通过大量分支路径推理，并整合历史点击序列以达到目标信息。
- **WorkArena**：反映办公室 / 企业员工更真实的工作流程。
- **AssistantBench**：测试遵循耗时、多轮工作流程的能力。
- **WebCanvas**：通过检查中间节点，在动态布局下挑战视觉解析与 UI 元素定位。
- **BEARCUBS**：专注知识密集型任务，要求检索并利用网页内容与外部知识源。

### 4.2 编程开发

评估 Agent 代码开发能力，一般通过单元测试评测执行结果，通常包括：1）能力测试（是否完成指令要求功能）；2）回归测试（是否破坏原有功能）。典型 Benchmark：**SWE-Verified**、**Terminal-Bench**。其它评估集：

- **WE-Agent**：提供检索、文件编辑等工具，以 Agent 形式完成 SWE 问题；另有在模态、语言、范式等方面有差别的类似 bench。
- **RepoBench**：评估仓库级代码补全能力。
- **SWT-Bench**：评测根据问题生成测试用例的 Agent 能力。
- **DevEval**：评估软件开发全过程（设计、环境设置、实现、测试）。
- **MLE-Bench**：提供 ML 相关仓库与 Linux 沙箱，要求 Agent 执行 ML 任务。
- **Pybench**：环境中引入 Python 代码解释器，Agent 操作不同类型文件完成真实任务（图表分析、文本分析、图像与音频编辑等）。

### 4.3 对话智能体

在支持、销售、辅导等领域与用户互动。与传统聊天机器人不同，它们维护状态、使用工具、在对话中途行动。典型 benchmark：**τ-bench**、**τ2**（模拟零售支持、机票预定、设备维修等）。评估时常用辅助 LLM 扮演用户；多通过检查最终环境状态（如是否预定成功机票）评估执行结果，有的通过 LLM 评估与用户交流的语气是否得当。

### 4.4 信息搜索

评估 Agent 通过搜索引擎收集信息的能力，通过带标准答案、用 LLM 或规则判断结果一致性。典型 benchmark：**browsecomp**、**GAIA**。

### 4.5 深度研究

评估 Agent 通过检索、收集信息、阅读文章等进行深度调研分析的能力，往往多维度评估：

1. **事实正确性**：检查结果是否得到检索资料支持；
2. **要点覆盖率**：是否包含关键信息；
3. **来源质量**：模型参考信息的权威性等。

### 4.6 科学研究

评估 Agent 作为专业研究员进行实际科学研究的能力：

- **ResearchArena**：基准测试收集调研信息与组织信息的能力。
- **SCIENCEWORLD**：文本环境测试科学推理（热力学、电路、化学反应、生物过程）。
- **DISCOVERYWORLD**：基准测试执行完整科学发现周期的能力。
- **ScienceAgentBench**：配备 bash shell、网页浏览器、代码解释器的环境，评估科学发现工作流编码。
- **MLGym**：类 gym 环境，Agent 可操作 shell、工具、Python 依赖、各类文件权限。
- **MLE-bench**：关注 Kaggle 挑战与竞赛，评估端到端 ML 工程能力，工作空间允许文件编辑与代码运行。
- **DSEval**：评估整个数据科学生命周期表现，运行时会话（Jupyter notebook）由内存数据、外部文件、执行历史、代码执行器组成。
- **ML-Bench**：Docker 容器内评估数据科学代码生成与仓库级代码操作能力。
- **Spider2-V**：专注数据科学自动化的多模态代理，依赖 Docker 进行文件传输、应用启动、远程 API 调用、脚本执行、Playwright 自动化。

### 4.7 计算机操作

评估 Agent 操作电脑完成任务的能力。典型 benchmark：**OSWorld**，最后用脚本检测任务完成后环境状态。其它：

- **OSWorld**：代表性桌面基准，用虚拟机（VM）构建可执行可控桌面环境；观察含桌面截图与无障碍（a11y）树；动作空间支持所有鼠标键盘操作（移动、点击等）；共 369 个任务（办公、OS、日常、工作流、专业）。**WindowsAgentArena** 专注 Windows 通用环境。
- **AgentStudio**：虚拟代理研究环境 + 工具 + 基准体系；环境可观察文本/图像/视频；动作空间同时支持 GUI 操作与 API 调用。
- **OmniACT**：评估通用自主代理的静态数据集，含自然语言任务、截图与 PyAutoGUI 脚本作为 ground truth。
- **OfficeBench**：专注办公任务；动作空间受限（取决于当前应用，如 run_command 仅在 Shell 有效）；可同时观察当前与前一状态。

### 4.8 手机操作

与计算机操作类似，场景换成手机系统：

- **B-MOCA**：较早的动态环境基准，含网络、购物、系统等简单日常任务。
- **AndroidWorld**：扩展 APP 范围，具备动态构建任务初始状态与无限变化任务参数的能力。
- **Mobile-Bench**：通过 API 操作扩展动作空间（如打开特定 APP 无需屏幕操作）；提出 checkpoints 评估规划/推理是否达关键节点。
- **A3**：专注日常 APP，提供更灵活动作空间（支持「长按」等）。
- **AndroidArena**：关注跨 APP 与受约束任务，需多 APP 协作并带约束（如「不要点击支付按钮」）。
- **MobileSafetyBench**：一系列安全相关任务（消息、银行应用操作）。

### 4.9 游戏

评估 Agent 挑战游戏的能力，一般用游戏系统自带评分作为最终得分：

- **SmartPlay**：全面评估多领域能力（长文本理解、推理、指令/规则遵循），涵盖视觉与文本游戏（Bandits、石头剪刀布、汉诺塔、Minecraft、Messenger、Crafter）；部分用内部奖励、部分用完成率。
- **VGRP-Bench**：专注益智游戏。
- **ING-VP**：评估基于图像空间关系的多步规划（推箱子、迷宫、数独、八皇后、汉诺塔、15-拼图）；指标含准确率、完成度、行动效率。
- **DSGBench**：严格评估平台，含星际争霸 II、文明等六款策略游戏，原始观察转文本提示；人工设计多指标（星际争霸 II：RPM、EER、SUR、TCR、APM、EPM、WR、GA 等）。
- **GameBench**：评估策略推理，九款多人棋盘游戏（ALS、ARC 等），用 Bradley-Terry 系统算相对分数。
- **GtBench**：以竞争模型方式评估。
- **GameArena**：评估中加入人类参与与反馈（如「AI Akinator」游戏，用户用「是/否」回答）。

## 五、Agent 评估的发展趋势

从多个角度梳理演化方向。

### 5.1 环境视角

- **单模态 → 多模态**：越来越多评估涉及非文本场景（VisualAgentBench、VideoWebArena 等）。
- **静态 → 演进**：从固定基准到动态不断更新（如 BFCL 系列手动不定时更新，WorkArena 需在线评估）。
- **无状态 → 有状态**：代理过去的交互与上下文会影响性能，更准确评估动态、持续任务，而非孤立场景。

### 5.2 代理视角

- **单代理 → 多代理**：焦点从独立运作的单代理，转向协作/竞争的多代理系统，引入协调、沟通、谈判等新挑战。
- 当前基准多以游戏/虚拟任务为主，缺乏反映现实协作（如基于互联网的团队合作）的场景；**MultiAgentBench**、**BattleAgentBench** 虽评估协调竞争，但未充分代表实际协作环境。
- 多数基准侧重同构多代理，忽略具专业技能（推理、检索、编码）的**异构代理**及现实层级结构（经理–执行者）；**DeepClaude**、**AgentVerse** 开始探索，但标准化基准仍不成熟。
- **单轮 → 多轮**：早期基准多为单轮（接收提示即响应），如单轮检索、端到端执行；随能力提高，Agent 可多轮对话更新需求，τ-Bench、WebLINX 已适配扩展交互。

### 5.3 评估者视角

- **人类评判 → Agent-Judge**：用基于代理的评估者（代理评判员）可显著扩展、无需额外人力；且随 AI 能力发展并在部分领域超越人类，人类评估可能不足以反映 Agent 全部潜力，故 Agent 评估 Agent 日益被视为必要演化。
- **通用 → 个性化**：多数代理为通用目的、按固定指令完成；部署到商业应用后需考虑用户偏好、个人资料、历史。如 **PetoolBench** 等个性化基准已出现，评估适应个体用户的能力。

### 5.4 指标视角

- **粗粒度 → 细粒度标签**：多数基准提供基于最终结果的粗粒度反馈；为捕捉细微差异，需更精细系统，如对决策过程的文本评论（「规划耗时过高」「决策快但有风险」），虽不适合直接比分数，但能给开发者更有价值见解。
- **有效性 → 效率**：如 **Worfbench**、**GOVSIM** 在评估有效性同时评估效率；未来基准需平衡二者，确保高效完成任务而不过度消耗资源/时间。

## 六、总结

本文从全局角度介绍 Agent 相关基本概念，系统梳理 Agent 评估的主要组件、与其它任务评估的不同特点、特有指标与具体方法，收集整理当前主流 Agent 场景，并对最新研究趋势与未来方向做简要总结。

Agent 评估的落地也与其它任务差别很大：要实现稳定、准确的执行与评估，涉及大量环节与细节；为实现高效率评估，对评估系统架构也提出不少挑战。这些内容将在后续系列文章系统介绍。
