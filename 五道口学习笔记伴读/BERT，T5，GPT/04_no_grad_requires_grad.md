## 〇、先补背景：什么是「梯度 / 反向传播」

03 学过 BERT 有 **1.1 亿个参数（旋钮）**。训练模型 = 不断**拧这些旋钮**，让输出更接近正确答案。

- **梯度（gradient）**：告诉每个旋钮「该往哪拧、拧多少」的方向标。
- **反向传播（backprop）**：算梯度的算法。
- 算梯度需要 PyTorch 在「前向计算」时**偷偷记下中间结果、建一张计算图**，回头好反推。

所以「要不要算梯度」直接影响**显存占用**和**计算量**——这正是下面两个工具要管的事。

> 衔接 03：03 警告里说「你应该在下游任务上 **TRAIN** 它（分类头）」——"train" 就是要算梯度、拧旋钮；而「冻结 body」就是不让某些旋钮被拧。

---

## 一、`torch.no_grad()`：临时「别算梯度了」

用 `with` 包一段代码（上下文管理器）：

```python
with torch.no_grad():
    outputs = model(input)   # 这段里完全不算梯度
```

**它做什么**：告诉 PyTorch「这块代码里别建计算图、别算梯度」。算出来的结果照常能用（预测、提取特征都行），只是**没有梯度**。

**关键特性**：
- **不改**任何参数的 `requires_grad` 标志——旋钮的「可训练」属性原封不动。
- 只是这次前向「跳过」了梯度记录。
- `with` 块一结束，梯度功能自动恢复正常。

**用在哪**：
- **推理 / 评估**（你 01 做情感分析时就是这么用的）：只想拿预测结果，不训练，没必要算梯度。
- 前向过程中只想「提取特征」、不想反向更新时。

---

## 二、`param.requires_grad = False`：永久「锁死这个旋钮」

对模块 / 层 / 每个参数改标志：

```python
for name, param in model.named_parameters():
    if param.requires_grad:
        param.requires_grad = False   # 把这个旋钮锁死
```

**它做什么**：直接把这个参数的 `requires_grad` 改成 `False`。从此该参数**不会被优化器更新、也不为它算梯度**——直到你手动改回 `True`。

**关键特性**：
- **真的改了标志本身**（和 `no_grad` 的根本区别）。
- 粒度到**模块 / 层**：可以只冻 encoder 前 6 层、只训后 6 层，非常灵活。

**用在哪**：
- **微调（fine-tuning）**：把 BERT 的 body（encoder）冻住，只让分类头（head）可训练。只训那一点点参数，既快又不易过拟合。
- 这正是 03 说的「身体复用、头按需换」在代码里的具体实现。

## 三、notebook 实验：最直观的区别证明

notebook 用 `calc_learnable_params` 数「`requires_grad=True` 的参数有多少个」。

**第一步**：刚加载的 BERT，所有参数可训练 → 数出 **109,482,240**（= 03 那 1.1 亿）。

**第二步**：在 `torch.no_grad()` 里再数：
```python
with torch.no_grad():
    print(calc_learnable_params(bert))   # 还是 109482240
```
**还是 1.1 亿！** 因为 `no_grad()` 只是「这次不算梯度」，**没动 `requires_grad` 标志**，所以计数不变。

**第三步**：真的把所有 `requires_grad` 设成 `False` 后再数：
```python
for name, param in bert.named_parameters():
    param.requires_grad = False
calc_learnable_params(bert)   # 输出 0
```
**变成 0 了！** 因为这次是**真把标志改了**，所有旋钮被锁死。

> 这个对比就是本 notebook 想教的全部：`no_grad()` 是「临时跳过」、不动标志；`requires_grad=False` 是「永久锁死」、改了标志。

## 四、两张表总结

### 4.1 no_grad vs requires_grad=False

| | `torch.no_grad()` | `param.requires_grad = False` |
|---|---|---|
| 本质 | 临时上下文（with 块内生效） | 永久改参数标志 |
| 是否改 `requires_grad` | **不改**（计数不变） | **改**（计数变 0） |
| 作用范围 | 块内**所有**计算 | 指定到**参数/层**级别（可只冻部分） |
| 计算图 | 整块不建图（省内存） | 只对该参数不算梯度，其他仍建图 |
| 典型用途 | 推理/评估、特征提取 | 微调时冻结 body、只训头 |
| 结束方式 | `with` 退出自动恢复 | 需手动设回 `True` 才恢复 |

### 4.2 一个常见组合（工业界微调标配）

```
推理时：            with torch.no_grad():  model(input)          # 啥都不训
微调时：            body.requires_grad=False  +  head.requires_grad=True  # 只训头
                   + 算梯度（不包 no_grad）
```

## 五、核心抉择：训 body 还是只训头？

### 5.1 先正名：那 1.1 亿到底是 body 还是「body + 头」？

**是 body 自己，不含任何任务头。**

03 的 `total_params` 是在 `BertModel.from_pretrained(...)` 上数的，而 `BertModel` = embeddings + 12 层 encoder + pooler，**没有**分类头、MLM 头、NSP 头（那些在加载时被丢弃，正是 03 那条警告）。挂上分类头后总数 ≈ 1.1 亿 + 1536，几乎不变——**头相对 body 是九牛一毛**。

### 5.2 不同头的参数确实不同

| 头 | 结构 | 大致参数量 |
|---|---|---|
| 分类头（情感） | `Linear(768→2)` | ~1536 |
| NSP 判断头 | `Linear(768→2)` | ~1538 |
| MLM 填空头 | `transform(768→768)` + `decoder(768→30522)`（常共享词表权重） | transform ~59 万 |
| pooler | `Linear(768→768)+Tanh` | ~59 万 |

无论哪个头，相对 1.1 亿 body 都极小。所以「只训头」= 训练参数只占 1.1 亿里的极小部分（1536 / 109M ≈ 0.0014%）。

### 5.3 「只训头 = 不改 body，只改翻译逻辑」——这句话完全正确

> 只训练 head 不就相当于不对 body 做修改吗，只是改变了翻译逻辑？

**完全正确。** 这就是「特征提取 / linear probing」的本质：body 当成固定的「语义压缩机」，参数永远不动；只有最顶上的「翻译官」（头）在学——学着把这串固定表示翻译成夸/骂。body 的 1.1 亿旋钮一颗不拧，只拧头的 1536 颗。

### 5.4 什么时候要训 body？什么时候只训头？

**只训头（冻结 body）适合**：
- 数据少（几百~几千条标注）：头太小，不易过拟合；
- 任务和预训练相近（通用英文 → 英文分类）：body 现成表示已够用；
- 想快、省显存、零风险：不存 body 梯度，训练飞快，也不会「忘了」预训练知识。

**训 body（全量微调）适合**：
- 数据量大（几万~上百万条）；
- 任务和预训练差得远（医学/法律等垂直领域、跨语言、跨模态）：body 通用表示不够用，得专门适配；
- 追求最高精度且算力充足。

### 5.5 差距对比

| 维度 | 只训头 | 训 body（全量微调） |
|---|---|---|
| 可训练参数 | ~0.001%（1536） | 100%（1.1 亿） |
| 所需数据 | 少 | 多 |
| 显存/算力 | 小 | 大 |
| 速度 | 快 | 慢 |
| 过拟合风险 | 低 | 高 |
| **性能上限** | **受限于 body 固定表示** | **更高** |
| 灾难性遗忘 | 无（body 不动） | 有 |

**核心差距一句话**：只训头省、稳、但天花板受 body 限制；训 body 贵、险、但上限更高——**本质是在「复用现成能力」和「为任务定制」之间权衡**。

## 六、LoRA：body 冻住，往里插一小撮可训练模块（这模块 ≠ head！）

> ⚠️ **易混淆点：LoRA 的模块不是 head。**

| | head（头） | LoRA 模块（适配器） |
|---|---|---|
| 位置 | **叠在 body 最顶上**（输出层） | **嵌在 body 内部**（每层 Linear 层旁边） |
| 作用对象 | 只对 `[CLS]` 那一个表示做翻译 | 改 body 内部「怎么处理信息」 |
| 改的是 | 翻译逻辑（最后一步） | 中间每一层的注意力/前馈行为 |

一句话：**head 是 body 外面的「嘴」，LoRA 是 body 里面的「小补丁」**——不在同一层。

### 6.1 LoRA 模块到底是什么

body 那 1.1 亿权重**原封不动冻结**，但在 body 内部的每个 `Linear`（比如 Q/K/V 那三个 `768→768`）**旁边，并联一个小旁路**：

```
原权重 W (768×768, 冻结, 不动)  ┐
                                 ├─ 相加 → 输出
旁路 BA (768×r × r×768, 可训练) ┘    其中 r 很小，比如 r=8
```

数学上：
```
输出 = W·x  +  (B·A)·x
       └原样┘    └──小补丁──┘
```
- `W` 永远冻结，1.1 亿旋钮一颗不拧；
- `B·A` 两个小矩阵**可训练**，参数量 ≈ `2 × 768 × r`，r=8 时约 1.2 万——比 head 还小。

训练时只算 `B、A` 的梯度、只拧这两个小矩阵的旋钮。**效果上等于在「微调 body 内部那 768→768 的变换」**，只是用旁路绕开了直接改 W。

### 6.2 为什么比「只训 head」强

- **只训 head**：body 是死的。若 body 给的表示本就不够好（如垂直领域文本），head 再怎么训也救不回来。
- **LoRA**：W 不动，但旁路 `BA` 能**调整 body 内部每一层处理信息的方式**——给身体打「微调补丁」，让它适配任务，又不真去动 1.1 亿原始旋钮。

介于两者之间：

| 方案 | 可训练参数 | 能否改 body 内部 | 上限 |
|---|---|---|---|
| 只训 head | ~1536 | ❌ 不能（只改翻译） | 受限于 body 固定表示 |
| **LoRA** | ~几万（r 小） | ✅ 能（旁路补丁） | 接近全量微调 |
| 全量微调 | 1.1 亿 | ✅ 能（直接改 W） | 最高 |

> 类比：head 像「换翻译官」；LoRA 像「给大脑每个部门配个随身小秘书，悄悄纠正部门处理习惯，但不动部门结构」；全量微调像「把整个公司重组」。

## 七、LoRA 训练前初始值 & 训练后怎么起作用

### 7.1 训练前初始值（最巧妙的一笔）

给每个旁路配两个矩阵 `A` 和 `B`（r 是秩，如 8）：
- **A**：随机小高斯初始化（均值 0、方差很小）。
- **B**：**初始化为全 0**。

结果：
```
训练前：  B·A = 0 × A = 0   （因为 B 是 0 矩阵）
```

所以训练**最开始那一刻**：
```
输出 = W·x + (B·A)·x = W·x + 0 = W·x
```
**完全等于原来的冻结模型！** LoRA 模块一挂上去时，对原模型**零影响**——和没加 LoRA 一模一样。

> 妙处：训练起点 = 原始预训练模型（已经很好），不会「一上来就破坏」现成能力。旁路再从零开始、一点点长出来适应任务。对比全量微调（直接在所有权重上加随机梯度），LoRA 起点稳得多。

### 7.2 训练完怎么起作用

训练结束后，`A` 和 `B` 被拧成两个固定的小矩阵，捕获了「你的任务」需要加在 body 内部的那点调整。起作用就一句话：
```
前向时：  每处理到一个 Linear 层
         该层输出 = 原 W·x   +   (B·A)·x
                    └原样┘        └训练好的补丁┘
```
`(B·A)` 是一个 `768×768` 的低秩矩阵（用 `768×8` 和 `8×768` 两个小矩阵拼成，省 99% 参数），**叠加在原权重输出上**，悄悄把这一层变换「掰」向任务。它**作用在 body 内部的每一层**（你指定哪层就加在哪层，通常是所有的 Q/K/V 投影层）。

### 7.3 两种部署方式

**① 分离模式（默认，最常用）**：
```
输出 = W·x + (B·A)·x
```
原 W 和旁路 BA **各算各的再相加**。好处：W 不动，**一个底座可挂多份 BA**——任务 A 加载 BA_A，任务 B 换 BA_B，瞬间切换。这正是「一个底座 + 多 LoRA」的用法。

**② 合并模式（merge，零开销）**：
```
W_merged = W + (B·A)
输出 = W_merged · x
```
推理时**没有任何额外参数、额外计算**，和全量微调后模型跑得一样快。代价：焊死后不能和别任务的 BA 切换了。

> 直觉：分离模式像「带可换配件」，合并模式像「把配件焊死」。看你要灵活还是要速度。

## 八、三者总览（本篇核心）

| 方案 | 可训练参数 | 改 body？ | 所需数据 | 速度 | 上限 | 灾难性遗忘 |
|---|---|---|---|---|---|---|
| 只训头 | ~1536（0.001%） | ❌ | 少 | 快 | 受限于 body | 无 |
| 全量微调 | 1.1 亿（100%） | ✅ 直接改 W | 多 | 慢 | 最高 | 有 |
| **LoRA** | ~几万（r 小） | ✅ 旁路补丁 | 中 | 快 | 接近全量 | 无（W 不动） |

> **一句话收**：body（encoder，贵，预训练好，产出通用语义表示）+ 小头（便宜，按任务接，翻译成答案）；LoRA 则是「body 原权重冻结 + 内部并联低秩补丁」，用 head 量级的代价拿到接近全量微调的能力。身体复用，头/补丁按需换——这就是现代 NLP「预训练 + 微调」范式的根本。

## 九、与已学知识的连接

1. **接 03 的 1.1 亿旋钮**：`requires_grad=False` 锁的就是这 1.1 亿里的指定部分；只训头 = 锁死全部 body、放开头的 1536；LoRA = 锁死全部 W、放开旁路 BA（约几万）。
2. **接 01 的 `no_grad`**：推理时用 `no_grad`（不训任何东西）；微调时是「body 锁 `requires_grad=False` + 头放开、算梯度」。
3. **接 03 的「TRAIN 它」警告**：正确做法是「encoder 冻（requires_grad=False）+ 分类头放开（requires_grad=True）」，或进一步用 LoRA 替代直接微调。
4. **接你 agent/RL 脉络**：LoRA/Adapter 的「冻主体、训小模块」，和 agent 里「共享底座 + 多技能」「防 hack、省算力」思路一脉相承，是大模型时代微调的主流方案。
5. **接 03 的「头」概念**：head 是 body **外面**的翻译官（读 `[CLS]` 做 `768→2`）；LoRA 是 body **内部**的补丁（每层输出加任务偏移）。两者可同时存在（body 冻 + LoRA 训 + 头也训）。
