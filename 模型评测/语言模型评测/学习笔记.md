## 1. 前置基础知识（评测前必须懂的模型侧知识）

评测岗不是「只会跑脚本」，JD 明确要求「深入理解大规模预训练语言模型」。以下是评测工作会直接用到的模型知识：

### 1.1 训练阶段与评测的对应关系

```
Pretrain ──► Base Model ──► SFT ──► Reward Model ──► RLHF/RLVR ──► Chat Model
   │             │            │           │                │            │
   ▼             ▼            ▼           ▼                ▼            ▼
 loss/PPL   few-shot客观题  指令遵循   RewardBench    对齐税/安全    Arena/MT-Bench
```

- **Base 模型**只能用 few-shot + loglikelihood 打分评测（它不会聊天，别用 chat 模板）
- **Chat 模型**必须套对 chat template，模板错了分数掉 10 个点是常事
- **Reward Model** 单独有 RewardBench 这类评测，属于 RLHF 链路质检
- **对齐税（Alignment Tax）**：RLHF 后客观题分数下降、主观分上升，评测报告必须同时给两侧

### 1.2 影响评测结果的模型侧变量（必背）

| 变量 | 影响 | 评测时怎么办 |
|---|---|---|
| 解码参数 temperature / top_p | 采样随机性 → 分数波动 | 客观题用 greedy（T=0）；采样题固定 seed 并多次取均值 |
| chat template | 模板不匹配 → 输出格式崩 | 用官方 tokenizer 的 `apply_chat_template` |
| system prompt | 影响指令遵循与拒答率 | 统一或明确报告 |
| max_new_tokens | 截断导致答案不完整 | 长 CoT 任务要给足（如 32k） |
| 量化 / 推理后端 | vLLM vs HF 结果有差异 | 同一批对比必须用同一后端 |
| few-shot 数量与顺序 | 显著影响 base 模型 | 固定 shot 与顺序，公开配置 |

> **面试高频**：「为什么你复现的 MMLU 和官方差 3 个点？」标准答案要能从上表逐条排查。

### 1.3 两种打分实现（必须理解差异）

1. **Loglikelihood 打分**（lm-evaluation-harness 默认）：分别计算 4 个选项的对数似然，取最大。不需要模型输出格式正确，适合 base 模型。有长度归一化问题（`acc` vs `acc_norm`）。
2. **生成式打分**（OpenCompass gen 模式）：让模型输出 "A"，再正则抽取。贴近真实使用，但依赖格式遵循能力，抽取失败要记为错。

同一模型同一数据集，两种方式分数可能差 5-10 分。**报告必须写明用的哪种**。

## 2. 评测维度体系（JD 的「指标体系制定」）

### 2.1 顶层能力树

```
LLM 能力
├── 知识类   MMLU / MMLU-Pro / C-Eval / CMMLU / AGIEval
├── 推理类
│   ├── 数学  GSM8K / MATH / AIME / FrontierMath
│   ├── 科学  GPQA Diamond
│   └── 逻辑  ARC-AGI / BBH
├── 代码类   HumanEval / MBPP / LiveCodeBench / SWE-bench
├── 指令遵循 IFEval / FollowBench
├── 长上下文 RULER / LongBench / NIAH
├── Agent    τ-bench / BFCL / AgentBench / GAIA / WebArena
├── 对话偏好 MT-Bench / Arena Elo / AlpacaEval-LC / Arena-Hard
├── 真实性   TruthfulQA / SimpleQA / HaluEval
├── 安全     HarmBench / SafetyBench / 越狱鲁棒性
└── 效率     TTFT / TPOT / 吞吐 / 每题成本
```

### 2.2 HELM 的关键启发（doc/HELM_*.pdf）

HELM 的核心主张：**不能只报准确率**。同一场景下要同时报 7 类指标：
准确率、校准性（calibration/ECE）、鲁棒性（扰动后掉多少）、公平性、偏见、毒性、效率。

> 这是给业务写评测方案时最好用的模板——大厂 JD 要求「多维度评测方案」，直接照 HELM 的 7 维展开就是一份专业方案。

### 2.3 维度设计的三条原则

1. **正交性**：维度之间尽量不重叠，否则加权总分会双重计算
2. **可判定性**：优先设计有唯一答案/可程序化校验的题（IFEval 是范本）
3. **区分度**：题目难度要覆盖梯度，全对或全错的题对排序无贡献（可借 IRT 思想筛题）

## 3. 指标的数学定义（面试要能手写）

**Accuracy / EM / F1**：基础，注意归一化（大小写、标点、数字格式）。

**pass@k**（HumanEval 提出，无偏估计）：
\[ \text{pass@}k = \mathbb{E}\left[1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}\right] \]
n 为总采样数，c 为通过数。直接用 "采 k 次看有没有对" 是有偏的。

**Elo / Bradley-Terry**（Arena 排名）：
\[ P(A \succ B) = \frac{1}{1+10^{(R_B-R_A)/400}} \]
在线 Elo 有顺序依赖，Arena 实际用 **BT 模型的 MLE** 拟合 + bootstrap 置信区间。

**长度控制胜率**（AlpacaEval-LC，doc/AlpacaEval_*.pdf）：
用 GLM 把「输出长度差」作为混淆变量回归掉，得到去除冗长偏好后的胜率。这是消除 judge 系统偏差的经典做法。

**校准（ECE）**：把预测置信度分桶，算 |平均置信度 − 实际准确率| 的加权和。衡量模型「知道自己不知道」。

**标注一致性**：Cohen's κ（两人）、Fleiss' κ / Krippendorff's α（多人）。做人评方案必须报这个数，否则数据不可信。

## 4. 核心论文精读要点（doc/ 目录）

### 4.1 MT-Bench & Chatbot Arena（`MT-Bench_Chatbot_Arena_LLM_as_a_Judge.pdf`）★最重要
- 提出 **LLM-as-a-Judge** 三种模式：pairwise comparison / single answer grading / reference-guided grading
- 系统量化三大偏差：
  - **位置偏差**：GPT-4 有明显偏好第一个答案 → 解法：交换顺序各评一次，不一致则判平局
  - **冗长偏差**：更长的答案更容易赢 → 解法：长度控制回归（AlpacaEval-LC）
  - **自我增强偏差**：judge 偏好自己家族的输出 → 解法：多 judge 投票 / 换 judge 交叉验证
- 关键结论：GPT-4 judge 与人类专家的一致率约 **80%+**，与人类之间的互相一致率相当 → 这是"LLM 判分可用"的最重要论据
- **面试必答**：怎么验证你的 judge 靠谱？→ 抽样人工标注，算 agreement rate 与 Spearman

### 4.2 HELM（`HELM_*.pdf`）
- 场景（scenario）× 指标（metric）× 适配（adaptation）三维矩阵的评测框架设计
- 强调 **standardization**：同一批模型在同一套 prompt 下全量跑，才可比

### 4.3 MMLU / MMLU-Pro（`MMLU_*.pdf`, `MMLU-Pro_*.pdf`）
- MMLU-Pro 的改进动作值得直接复用到自建评测集：
  1. 4 选项 → **10 选项**（随机基线 25% → 10%）
  2. 剔除噪声题与过简题
  3. 增加需要推理的题 → CoT 增益从"负"变"正"
  4. 验证**对 prompt 变化更鲁棒**（分数标准差从 4-5% 降到 2%）
- 启发：**benchmark 饱和后的升级路线 = 加干扰项 + 提难度 + 清洗噪声 + 验证鲁棒性**

### 4.4 LiveBench（`LiveBench_*.pdf`）★抗污染范式
- 三个设计：题目来自**最近发布**的信息源（arXiv、新闻、竞赛）；**每月更新**；答案**客观可自动判定**（不用 LLM judge）
- 解决了两大痛点：训练集污染 + judge 偏差
- 启发：企业内部评测集也应「持续滚动更新 + 保留私有 holdout」

### 4.5 SWE-bench（`SWE-bench_*.pdf`）
- 从 GitHub 真实 PR 构造：issue 描述作为输入，**单元测试是否通过**作为判定（FAIL_TO_PASS / PASS_TO_PASS）
- 评测工程重点：**容器化沙箱**、依赖环境复现、执行超时、防止 agent 作弊（直接改测试文件）
- 这是「把开放式任务转成可判定任务」的最佳范例，也是评测平台工程能力的试金石

### 4.6 τ-bench（`tau-bench_*.pdf`）
- 引入 **user simulator**（LLM 扮演用户）做多轮交互，评测 agent 能否遵守 domain policy 并完成任务
- 指标：`pass^k`（同一任务独立跑 k 次全部成功的概率）→ 衡量**可靠性/一致性**，而非单次成功
- 关键发现：先进模型 pass^1 尚可，pass^8 暴跌 → 「一致性」是被传统指标掩盖的短板
- **这个指标思路很值得在业务评测中复用**

### 4.7 Arena-Hard / BenchBuilder（`Arena-Hard_*.pdf`）
- 从 Arena 真实用户流量中**自动筛选**高质量 prompt 的流水线：7 条质量标准打分（是否具体、是否需领域知识、是否复杂…），聚类去重
- 产出的评测集与人类偏好的**可分离度（separability）与一致性**都优于 MT-Bench
- 对应 JD 里「构建自动化评测数据合成管线」，这篇是最直接的落地参考

### 4.8 RewardBench（`RewardBench_*.pdf`）
- 评测 RM 的四大类：Chat / Chat-Hard / Safety / Reasoning，每条是 (prompt, chosen, rejected) 三元组，看 RM 是否给 chosen 更高分
- 做 RLHF 训练侧评测必备

## 5. 评测集怎么造（JD 高频要求）

### 5.1 标准流程

1. **需求拆解**：业务想知道什么 → 能力维度 → 每维度多少题
2. **数据来源**：真实用户日志（脱敏）> 专家撰写 > 公开数据改造 > 纯合成
3. **难度与分布设计**：难度梯度、领域分布、长度分布，避免头部集中
4. **标注规范（Rubric）撰写**：这是评测岗的核心交付物，需包含
   - 任务定义与评分维度（如：正确性 / 完整性 / 格式 / 安全）
   - 每档分数的**具体行为描述 + 正反例**
   - 边界情况处理（拒答、部分正确、超纲）
5. **试标 → 计算 κ → 修订规范 → 正式标注**（一致性 < 0.6 必须回炉改规范）
6. **质检**：黄金题抽检、标注员一致性监控、争议题仲裁
7. **污染检测与版本管理**：公开 dev 集 + 私有 test 集

### 5.2 污染检测方法
- **n-gram 重叠**：13-gram 与训练语料匹配（GPT-3 论文做法）
- **Canary string**：数据集内嵌唯一标识串，检查模型是否能背出
- **时间切分**：比较模型 cutoff 前后题目的分数差
- **扰动测试**：改写题目/换选项顺序，分数暴跌说明是背题
- **困惑度对比**：污染样本的 PPL 异常低

## 6. 工程化落地（字节 JD 重点）

### 6.1 自动化评测 Pipeline 架构

```
配置层 (YAML: 模型/数据集/prompt模板/解码参数)
   │
任务调度 (分片、并发、断点续跑、失败重试)
   │
推理层 (vLLM/SGLang 本地  |  OpenAI-compatible API)
   │
后处理 (答案抽取、归一化、抽取失败标记)
   │
判分层 (规则判分 | 代码执行沙箱 | LLM Judge | RM 打分)
   │
聚合层 (分维度得分、置信区间、bootstrap)
   │
报告层 (对比表、雷达图、bad case 归类、回归对比历史版本)
   │
闭环 (接 CI：训练 checkpoint 自动触发评测 → 结果回写训练看板)
```

### 6.2 必须处理的工程细节
- **可复现性**：记录 model hash、数据集版本、prompt 模板、解码参数、框架 commit
- **成本控制**：judge 调用缓存（相同输入命中缓存）、分层评测（先小集筛，再大集验）
- **并发与限流**：API 模型的 RPM/TPM 限制，指数退避
- **沙箱安全**：代码执行类评测必须容器隔离 + 超时 + 网络隔离
- **回归看板**：每个 checkpoint 的分数曲线，识别训练退化

### 6.3 主流框架对比

| 框架 | 优势 | 适用 |
|---|---|---|
| OpenCompass | 中英数据集最全、配置化、国内大厂主流 | 中文场景首选 |
| lm-evaluation-harness | 国际标准、HF 榜单底座、loglikelihood 打分严谨 | 对齐国际论文数字 |
| EvalScope | 评测 + 性能压测一体（阿里） | 需要同时测效果与性能 |
| FastChat | MT-Bench / Arena 实现 | 主观评测与 judge |
| DeepEval / Ragas / promptfoo | 面向应用层（RAG、prompt 回归） | 业务侧评测 |

## 7. 结果分析与归因（JD：「产出客观认知，指导训练迭代」）

评测报告不能只给一张分数表，要给出**可执行结论**：

1. **分维度对比**：雷达图 + 与竞品/上一版本的 delta
2. **Bad case 聚类**：把错题按错误类型归类（知识缺失 / 推理断链 / 格式不遵循 / 幻觉 / 拒答过度 / 抽取失败）
3. **能力边界刻画**：按难度分档看准确率衰减曲线，找出"崩溃点"
4. **归因到训练**：某维度低 → 是数据不足？SFT 配比问题？RLHF 过度对齐？
5. **统计显著性**：两个模型差 0.5 分是否显著？给 bootstrap 置信区间，别报噪声
6. **成本-效果曲线**：同等成本下的最优模型，业务决策更看这个

> 面试常问：「模型 A 比 B 高 2 分，你的结论是什么？」
> 好答案 = 先看置信区间是否重叠 → 再看是哪些子维度贡献的 → 再看 bad case 类型是否不同 → 再考虑是否有污染/格式优势 → 最后才下结论。
